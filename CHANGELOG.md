# Changelog

All notable changes to this project are documented in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/) from `1.0.0` onward.

## [1.1.0] - 2026-09-22

The first sub-release of the `v1.1` milestone (`v1.1a`, "security-relevant policy gaps", tracked in `docs/superpowers/specs/2026-09-11-v1.1-scope-design.md`), closing the ten highest-priority issues from that milestone's 32. Findings came from two sources: the remainder of the original tier-charter audit, and an independent agy/Gemini 3.1 Pro (High) cross-model review of the whole repo. Later sub-releases (`v1.1b` onward: correctness/coverage, reliability/packaging, test coverage, new capability, documentation) will ship as their own subsequent versions rather than waiting for the full milestone.

### Fixed

- **#48**: `dnf install /path/to/local.rpm` matched `standard` tier's `^install` allow with no denied flag involved. dnf4's `localpkg_gpgcheck` defaults to `false`, so on a host with that default, installing a local RPM ran its scriptlets as root with no signature check at all, a full trust bypass reachable without any of the flags the existing `DNF_TRUST_BYPASS_FLAGS` deny was watching for.
- **#52**: `ROOT_REQUIRED_TOOLS` included `vmstat`, `sar`, `top`, and `ping`, despite these reading only world-readable `/proc`/`/var/log/sa` and not needing real privilege to do anything useful. Live-verified unprivileged-safe and removed from the root-required set, tightening the tier boundary to match actual need.
- **#54**: startup validation for `developer` tier checked only that `developer_user` resolves to a non-root uid. It did not check whether that account had sudo access of its own. A `developer_user` carrying a user-named `NOPASSWD` sudoers entry (e.g. `developer_user ALL=(ALL) NOPASSWD: ALL`) defeated the tier boundary entirely, since sudo re-escalation was never in scope for what the tier's own privilege-drop mechanism was checking. RedWrench now warns at startup when this configuration is detected.
- **#58**: `custom_rules` are deliberately prepended ahead of every tier rule, which is what makes custom *denies* work. The undocumented consequence was that a custom *allow* for a command silently disabled that command's existing tier-level hardening denies too, with no warning that the operator had just reopened something the tier was built to close. RedWrench now warns when a `custom_rules` allow shadows an existing tier-level deny.
- **#59**: `Config::load` validated a custom rule's command with `r.command.trim().is_empty()` but stored the untrimmed value, while `PolicyEngine::evaluate` compares commands with an exact string match. A `custom_rules` command entered with leading or trailing whitespace loaded successfully and looked correct in config, but silently never matched anything, a rule that appears active but is permanently inert. Fails closed, so a usability bug rather than a security one, but the same "a control silently disappears" shape the project already guards against elsewhere in `config.rs`. Now trimmed before storage, matching the emptiness check's own behaviour.
- **#71**: `standard` tier's `rpm-ostree` allow (`^(install|upgrade|status|uninstall)`) had no deny keyed to `--reboot`/`-r`, letting `rpm-ostree upgrade --reboot` reboot the host through a route the existing systemd reboot-lockdown (`v1.0.1`, #40) never anticipated, since it only watched `systemctl`/`systemd` targets and units.
- **#72**: the `developer`-tier privilege-drop path set exactly three environment variables (`HOME`, `USER`, `LOGNAME`) before spawning the child process, with no `cmd.env_clear()` anywhere in `executor.rs`. `tokio::process::Command::env()` merges into the *inherited* environment rather than replacing it, so the spawned process ran with root's full environment intact underneath the three overrides, a potential credential and configuration leak across the privilege boundary. The environment is now cleared before the three identity variables are set.

### Documented, not fixed (verified non-issues or already-correct-but-fragile)

- **#46**: `sar`'s clustered `-o` flag (`sar -uo /tmp/evil.dat`) was flagged as a possible arbitrary root file write at `safe` tier. Live-verified against the real sysstat argument parser: clustering does not reach `-o` the way the finding hypothesised. Confirmed not a bug; documented rather than changed.
- **#51**: the dnf trust-bypass deny (`DNF_TRUST_BYPASS_FLAGS`) currently survives only because rule ordering happens to place it after all of `safe` tier's rules, of which none currently allow `dnf`. That's not a structural guarantee, a future `safe`-tier `dnf list` addition could silently reintroduce the gap. Documented as a fragility, with a pre-emptive regression test added (currently ignored, meant to start failing the moment such an addition lands).
- **#75**: `run_command` has no `--` separator ahead of user-controlled tail arguments, unlike the dedicated tool routers (`dnf.rs`, etc.), leaving its injection defence resting entirely on the `tiers.rs` regexes rather than defence-in-depth. Assessed by an independent cross-model review, and confirmed by independent verification, as not currently exploitable. Documented as a discipline note for future work, with a regression test added.

## [1.0.1] - 2026-09-10

A security patch closing five findings from an independent tier-charter audit (`docs/superpowers/specs/2026-09-10-tier-charter-audit.md`), all affecting `v1.0.0`. Two of the five affect every tier except `unrestricted`, since every tier inherits `safe`'s rules.

### Fixed

- **#38, critical**: `journalctl`'s bare `+` disjunction operator let a query carry a real, glob-free unit scope while OR-combining it with other appended match expressions, reopening a whole-journal read at `safe` tier by a route the original `#26` fix didn't anticipate.
- **#39, high**: `top -b -c` at `safe` tier disclosed every process's full command line, system-wide, as root, the same confidentiality class as `#26`, never previously scoped.
- **#40, high**: `standard` tier could reboot, power off, or drop the host to single-user mode via `systemctl start`/`restart` against `reboot.target`/`poweroff.target`/`halt.target`/`emergency.target`/`rescue.target`, ordinary service-lifecycle syntax the tier's own allow pattern didn't distinguish from a real service. Closed across three rounds: the first named those five targets directly; a reopen found eight further shipped `.target` equivalents (runlevel aliases, `ctrl-alt-del.target`, `kexec.target`, and others) the literal list missed, closed by replacing it with a structural deny on any `.target` argument under the lifecycle verbs (`start`/`stop`/`restart`/`enable`/`disable`); a second reopen found that plain `.service` units carrying `SuccessAction=`/`FailureAction=` directives (`systemd-poweroff.service` and its `-reboot`/`-halt`/`-kexec`/`-soft-reboot`/`-exit`/`-factory-reset-reboot` siblings, plus `system-update-cleanup.service`) reach the same reboot/power-off/halt outcomes with no `.target` in argv at all, live-confirmed by powering off a running system through the exact command the server would issue, closed by naming those units alongside the `.target` deny. **If you are upgrading from `v1.0.0` and your own runbook or `custom_rules` reference a `.target` unit under `standard` tier (e.g. `systemctl enable remote-fs.target`), that unit is now denied by default; grant it explicitly via `custom_rules` if you rely on it.**
- **#41, critical**: `dnf -c`/`--config` (and several other flags) were not covered by the package-trust-bypass deny, letting an alternate config file achieve `--nogpgcheck` and `--repofrompath` together with no denied flag involved, a full root-escalation chain under `developer` tier. Closed across four review rounds after live testing against real `dnf4`/`dnf5` binaries surfaced clustered short options (`-yc`, `-4c`), dnf's prefix-abbreviation (`--con`, `--i`, `--des`), a digit-inclusive character class the first two fixes missed, and dnf5's distinct `--no-gpgchecks` long-option spelling (not reachable via the `--nog` prefix that already covered `--nogpgcheck`), the last of which is the default `dnf` on Fedora 41+ and this project's own deployment target.
- **#42, critical**: a `custom_rules` entry unconditionally allowing a command (e.g. `bash`) under `safe`/`standard` tier granted unfiltered root code execution with no warning and no `--i-understand-the-risk` requirement, since those tiers have no privilege-drop mechanism. RedWrench now refuses to start on such a configuration without the flag. Closed across three rounds: the first checked only the unconditional (`None`) case, the second closed a catch-all `arg_pattern` (`.*`, `^`, `$`) that was functionally unconditional but technically distinct, and the third extended the same gate to `developer` tier for commands in `ROOT_REQUIRED_TOOLS` (`dnf`, `systemctl`, `journalctl`, etc.), which that tier's privilege drop does not cover. **If you are upgrading from `v1.0.0`: a config with an unconditional (`arg_pattern` omitted) `custom_rules` allow under `safe`/`standard` tier, or under `developer` tier for a `ROOT_REQUIRED_TOOLS` command, will now refuse to start until you either add an `arg_pattern` restriction or pass `--i-understand-the-risk`.**

## [1.0.0] - 2026-09-10

The first tagged release. RedWrench exposes Fedora hardware and OS control to AI coding agents over MCP, behind a tiered, ordered allow/deny policy engine, with every invocation recorded to the systemd journal.

### Added

- **Policy engine**: an ordered, first-match-wins allow/deny rule set with four tiers (`safe`, `standard`, `developer`, `unrestricted`), each extending the one below it, plus operator-configurable `custom_rules` layered on top via `config.toml`.
- **Developer tier**: privilege-dropped execution of a fixed set of interpreters and build tools (`bash`, `sh`, `python3`, `gcc`, `cc`, `node`, `npm`, `cargo`, `make`) under a configured non-root identity, with a real Unix privilege drop (`setgroups`→`setgid`→`setuid`) as the actual security boundary, not command filtering.
- **Structured tools**: `systemctl_status`/`systemctl_control`, `dnf_install`/`dnf_remove`, `journalctl_tail`, `ping`, `run_command` for everything else, each argument-injection-hardened against flag-abbreviation and clustered-short-option bypasses.
- **Streaming execution**: live output via `notifications/progress`, cooperative cancellation via `notifications/cancelled`, and a server-enforced safety-net duration for indefinite commands.
- **Capability and policy discovery**: `list_capabilities` and `check_command`, both allowed at every tier since they only introspect the policy engine and never execute, plus self-teaching denial messages that name a tier that would allow a denied command. README and ARCHITECTURE.md exposed as MCP resources.
- **Audit trail**: every invocation, allowed or denied, recorded to the systemd journal with the active tier, resolved command, and outcome.
- **Transport**: MCP over Streamable HTTP, bearer-token authenticated, with a DNS-rebinding host allowlist and an explicit guard against binding to a public address without an override flag.
- **UAT scenarios** (`docs/uat/v1-uat-scenarios.md`): manual verification scenarios covering every tier, the audit trail, streaming, cancellation, and the discovery tools, run against a real Fedora box over Tailscale.

### Known limitations, deliberately deferred

These were the original design spec's own v1.0 non-goals, not gaps discovered late:

- No deep Tailscale-specific integration (per-device identity in authorisation), see #6.
- No real-time interactive approval workflow (a pending-request-to-phone model), see #5.
- No `systemd-sysext` packaging for immutable Fedora variants, see #3.
- Not submitted to COPR or Fedora's official repositories, see #4.
- No GUI configuration app, see #30.
