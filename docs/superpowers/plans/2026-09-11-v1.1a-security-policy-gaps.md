### Task 1: `rpm-ostree --reboot` bypasses the systemctl reboot lockdown (#71)

**Files:**
- Modify: `src/policy/tiers.rs`

**Interfaces:**
- Consumes: existing `allow()`/`deny()` helpers, the `standard_rules()` function's existing `"rpm-ostree"` allow rule.
- Produces: a new `RPM_OSTREE_REBOOT_FLAG` deny constant and rule, used only within this task.

**The gap:** `standard` tier's `rpm-ostree` allow (`^(install|upgrade|status|uninstall)`) matches the leading subcommand only and applies no restriction to the flags that follow. `rpm-ostree` accepts a `-r`/`--reboot` flag on `install`, `upgrade`, and `uninstall` (confirmed live against `rpm-ostree --help` on a current Fedora container: `status` has no such flag) that reboots the host immediately once the transaction completes. `rpm-ostree upgrade --reboot` is genuinely allowed today, sidestepping the systemctl-specific reboot restrictions `SYSTEMCTL_TARGET_LIFECYCLE` closes on the systemctl side entirely.

**Already live-verified while writing this plan** (re-verify independently, do not skip): on a fresh `fedora:latest` container with `rpm-ostree` installed, `rpm-ostree upgrade --reb` was rejected with `error: Unknown option --reb` (no prefix abbreviation), `rpm-ostree upgrade -r` and `rpm-ostree upgrade -rq` (clustered with `-q`, `--quiet`) both passed option parsing and reached the runtime `error: This system was not booted via libostree` message, confirming clustering is accepted by rpm-ostree's option parser (unlike the abbreviation question), while `rpm-ostree upgrade -x` (an invented flag) was rejected at the parsing stage with `error: Unknown option -x`. No other short option beginning with `r` exists under `install`, `upgrade`, or `uninstall` (confirmed via `rpm-ostree <subcommand> --help`), so a `-[A-Za-z]*r` pattern cannot collide with any real flag.

- [ ] **Step 1: Add the new deny constant, immediately after `SYSTEMCTL_TARGET_LIFECYCLE` in `src/policy/tiers.rs`**

```rust
/// (issue #71) `rpm-ostree` accepts a `-r`/`--reboot` flag on `install`,
/// `upgrade`, and `uninstall` that reboots the host immediately once the
/// transaction completes (confirmed live via `rpm-ostree <subcommand>
/// --help`; `status` has no such flag). `standard` tier's `rpm-ostree`
/// allow matches the leading subcommand only and says nothing about the
/// flags that follow it, so `rpm-ostree upgrade --reboot` is allowed
/// today with no deny in the way, sidestepping `SYSTEMCTL_TARGET_LIFECYCLE`
/// entirely since that deny is keyed to the `systemctl` command only.
///
/// Live-verified against real `rpm-ostree` on a current Fedora container:
/// no abbreviation of `--reboot` is accepted (`--reb` is rejected as
/// "Unknown option"), but clustered short options are accepted (`-rq`
/// passes option parsing, matching `-r` and `-q` together), and no other
/// short option under `install`/`upgrade`/`uninstall` begins with `r`, so
/// a clustered-form-aware pattern cannot collide with any legitimate
/// flag. Mirrors the deny-before-allow pattern already used for `dnf`
/// and `systemctl` in this file.
const RPM_OSTREE_REBOOT_FLAG: &str = r"(?:^|\s)(?:--reboot|-[A-Za-z]*r)";
```

### Task 2: developer-tier privilege drop leaks root's environment to the child (#72)

**Files:**
- Modify: `src/executor.rs`

**Interfaces:**
- Consumes: the existing `execute()` function's `DeveloperIdentity` branch (around the `cmd.current_dir(home).env(...)` call).
- Produces: no new public interface; the fix changes `execute()`'s internal behaviour only.

**The gap:** `execute()`'s developer-identity branch sets exactly `HOME`, `USER`, and `LOGNAME` via `.env(...)` calls, which only insert or override individual keys into the *inherited* environment. There is no `cmd.env_clear()` anywhere in the file. Since RedWrench itself runs as root (`redwrench.service`'s `User=root`), the privilege-dropped child inherits root's full environment: `PATH`, any `LD_PRELOAD`, `XDG_RUNTIME_DIR=/run/user/0`, and anything else present in the service's environment, undermining the isolation guarantee README describes for `developer` tier.

### Task 3: `sar`'s clustered `-o` (#46), live-verified: not a bug, doc correction

**Files:**
- Modify: `src/policy/tiers.rs`

**Interfaces:**
- Consumes: the existing `SAR_FILE_OUTPUT_FLAG` constant and its doc comment.
- Produces: no behavioural change; corrects an inaccurate doc-comment claim and adds a regression test locking in the confirmed-safe finding.

**The gap, as filed:** whether `sar -uo /tmp/evil.dat 1 1` clusters as `-u -o file` (bypassing the deny, since the existing regex would need the clustered form to still contain a matchable `-o`) was unconfirmed without live testing.

**Already live-verified while writing this plan** (re-verify independently, do not skip): on `fedora:latest` (sysstat 12.7.9), `sar -uo /tmp/evil.dat 1 1` was rejected outright with a usage error (exit code 1); `sar`'s own usage text lists `-o [ <filename> ]` as a standalone bracketed alternative, separate from the activity-letter group (`-A`, `-B`, `-b`, ..., `-u [ALL]`, ...), confirming `-o` cannot cluster with any activity letter in either order (`-uo` and `-ou` were both tested and both rejected; `-bo` was also tested and rejected). Separately, and worth correcting: the existing doc comment on `SAR_FILE_OUTPUT_FLAG` claims sar accepts an attached-form output path with no separator (`-ofile.dat`); live testing found this is false for sysstat 12.7.9, `sar -oevil4.dat 1 1` (attached, relative path) was rejected with the same usage error, only the space-separated form `sar -o evil5.dat 1 1` works and creates the file. This does not weaken the existing deny (the regex `(?:^|\s)-o` with no trailing boundary already matches both forms regardless of which one sar actually accepts), but the comment states something false about sar's real behaviour and should say what was actually verified instead.

**Verdict for this task: #46's concern is REFUTED.** No clustering bypass exists. Close with a regression test and a corrected doc comment, not a new deny rule (the existing one is already sufficient and does not need to change).

### Task 4: `dnf install` of a local RPM bypasses signature verification (#48)

**Files:**
- Modify: `src/policy/tiers.rs`

**Interfaces:**
- Consumes: existing `allow()`/`deny()` helpers, `standard_rules()`'s existing `"dnf"` allow rule.
- Produces: a new `DNF_LOCAL_PACKAGE_PATH` deny constant and rule, used only within this task.

**The gap:** `dnf install /path/to/local.rpm` matches `standard` tier's `^(install|remove|upgrade)` allow with no denied flag involved at all, since there's no flag, just a path argument where a repo package name is expected. dnf's `localpkg_gpgcheck` setting controls whether a locally supplied RPM file gets signature-checked before its scriptlets run as root, independently of `gpgcheck` (which governs repository packages).

**Already live-verified while writing this plan** (re-verify independently, do not skip): on `fedora:latest` (dnf5 5.4.3.0, Fedora's current default `dnf`), `dnf5 --dump-main-config` shows `gpgcheck = 1` (repository packages are checked) but `localpkg_gpgcheck = 0` (a locally-supplied RPM file is installed with no signature check at all). This confirms the concern live, on the project's own current default deployment target: installing a local RPM runs its scriptlets as root with no trust verification whatsoever, a materially weaker posture than the "signed package in a configured repository" guarantee `standard` tier otherwise relies on.

- [ ] **Step 1: Add the new deny constant, immediately after `DNF_TRUST_BYPASS_FLAGS` in `src/policy/tiers.rs`**

```rust
/// (issue #48) `dnf install /path/to/local.rpm` matches `standard` tier's
/// `^(install|remove|upgrade)` allow with no denied flag involved at all,
/// since there's no flag, just a path where a repository package name is
/// expected. `dnf`'s `localpkg_gpgcheck` setting controls whether a
/// locally-supplied RPM file gets signature-checked before its scriptlets
/// run as root, independently of `gpgcheck` (repository packages).
///
/// Live-verified on a current Fedora container (dnf5 5.4.3.0, Fedora's
/// current default `dnf`): `gpgcheck = 1` but `localpkg_gpgcheck = 0`, so
/// a local RPM file is installed with no signature check at all today, on
/// this project's own default deployment target.
///
/// Matches an argument that looks like a filesystem path (starts with
/// `/`, `./`, or `../`) or a `.rpm` filename (ends in `.rpm`), rather
/// than an ordinary repository package name, which never takes either
/// shape in practice. `\S*\.rpm` requires the literal substring `.rpm`,
/// so it does not false-positive on a package merely containing the
/// letters "rpm" with no preceding dot (e.g. `rpmlint`).
const DNF_LOCAL_PACKAGE_PATH: &str = r"(?:^|\s)(?:\.{0,2}/\S*|\S*\.rpm)(?:\s|$)";
```

```rust
/// `developer_user` resolves to a non-root uid. It says nothing about
/// whether that account can `sudo` back to root, which would defeat the
/// entire tier: any dropped command could trivially re-escalate via

        .args(["-l", "-U", username])

             dropped to this account under 'developer' tier can potentially \
             re-escalate to root via sudo, defeating the tier's privilege-drop \
             guarantee. Review this account's sudoers configuration if this is \
             unintentional. ('sudo -l -U {username}' reported: {})",
            stdout.trim()

}
```

```rust
/// explicitly authored this allow, it is a config-review nudge, not a

    custom_rules: &[policy::Rule],
) -> Vec<String> {
    let tier_rules = policy::tiers::rules_for_tier(tier);
    let mut warnings = Vec::new();
    for rule in custom_rules {
        if !matches!(rule.effect, policy::Effect::Allow) {
            continue;
        }
        let is_unconditional = match &rule.arg_pattern {
            None => true,
            Some(pattern) => pattern.is_match(""),
        };
        if !is_unconditional {
            continue;
        }
        let shadowed: Vec<&str> = tier_rules
            .iter()
            .filter(|r| r.command == rule.command && matches!(r.effect, policy::Effect::Deny))
            .map(|r| r.description.as_str())
            .collect();
        if !shadowed.is_empty() {
            warnings.push(format!(
                "custom_rules unconditionally allow '{}', which reinstates behaviour \
                 the '{}' tier otherwise denies for that command: {}. Since \
                 custom_rules are evaluated before tier rules, this custom allow \
                 makes those denials unreachable for '{}'.",
                rule.command,
                policy::tiers::tier_display_name(tier),
                shadowed.join("; "),
                rule.command
            ));
        }
    }
    warnings
}
```

### Task 10: `run_command` has no `--` separator, injection defence rests entirely on `tiers.rs` regexes (#75)

**Files:**
- Modify: `src/tools/run_command.rs`
- Modify: `src/policy/tiers.rs` (test only, no rule change)

**Interfaces:**
- Consumes: nothing new.
- Produces: a doc comment on `run_command`'s tool handler documenting the invariant explicitly, plus a regression test proving the invariant holds today for at least one existing tool.

**The gap, as filed and self-assessed by the reviewing agent:** dedicated tool routers (`dnf.rs`, `systemctl.rs`, `network.rs`) inject a literal `--` separator before user-controlled tail arguments; `run_command` does not, it passes raw MCP-call arguments straight to `dispatch`. `PolicyEngine::evaluate` makes no distinction between a call that came through a dedicated router and one that came through `run_command`, both hit the identical rule set.
