# v1.1 Scope and Sequencing Design

**Status:** approved by Simon, 2026-09-11. Feeds `superpowers:writing-plans`, one plan per sub-release below.

## Why this document exists

v1.1's milestone carries 32 issues, filed from three sources: the original tier-charter audit's medium/low-severity remainder, an independent agy/GPT-OSS 120B cross-model review (#65-#69, most of that pass's higher-severity claims were refuted on inspection and are not included here), and an independent agy/Gemini 3.1 Pro (High) cross-model review (#71-#75, all five findings survived independent verification against the real source). Most individual issues already carry a proposed fix in their GitHub issue body; the design work this document captures is sequencing and grouping, plus settling the one issue (#22) that's genuinely new capability rather than a gap fix.

32 issues is too large for one implementation plan or one final review to hold with real scrutiny. This document decomposes v1.1 into six sequential sub-releases, each its own plan, branch, and PR, following the same subagent-driven-development process v1.0.1 used (implement, task-review, whole-branch final review, scoped re-review of any fix wave, merge).

## Sequencing

Security severity first, additive capability last. Each sub-release ships independently; later ones are not blocked on earlier ones except where noted.

### v1.1a, security-relevant policy gaps (10 issues)

#71, #72, #46, #48, #51, #52, #54, #58, #59, #75.

Highest priority: #71 (`rpm-ostree --reboot` bypasses the reboot lockdown) and #72 (developer-tier privilege drop leaks root's environment) are the same severity class as v1.0.1's #40-#42. The remaining eight are lower-severity or need investigation before the fix is known.

**Live-verification items:** #46 (`sar`'s clustered `-o` may permit an arbitrary root file write), #48 (local RPM install may bypass signature verification depending on dnf's `localpkg_gpgcheck` default), #52 (`ROOT_REQUIRED_TOOLS` may be broader than necessary). Per Simon's direction, verification is not a separate spike: each task's plan includes the exact live-verification steps (matching v1.0.1's plan style), and the implementer runs verification first, then applies whichever fix the result calls for. If verification finds no real issue, the task closes with a documented "not a bug" finding rather than a forced fix.

### v1.1b, correctness/coverage gaps (5 issues)

#43, #45, #49, #50, #60. Policy engine precision fixes with no live-verification dependency, each with a clear fix already stated in its issue.

### v1.1c, reliability/packaging (4 issues)

#73, #74, #25, #68. Operational correctness, not security: the postun-restart kill risk, cosmetic UTF-8 streaming corruption, an unbounded-block risk on `run_command`, and systemd unit hardening (evaluated for compatibility with RedWrench's own root-running execution model, not applied blindly).

### v1.1d, test coverage (5 issues)

#35, #57, #65, #66, #67. Locks in current and newly-fixed behaviour with real tests. Sequenced after a/b/c so new tests reflect the corrected code, though none of these five issues have a hard dependency on the earlier sub-releases' fixes landing first.

### v1.1e, documentation (7 issues)

#44, #47, #53, #55, #56, #69, #70. Includes the client-connection gap Simon raised directly (#70: README never shows how to actually connect Claude Code, Codex, or Antigravity to a running instance, no endpoint URL, no client config snippet, no bearer-token wiring). No code changes; sequenced after the code sub-releases so documentation describes the final, corrected v1.1 behaviour rather than needing a second pass.

### v1.1f, new capability (1 issue)

#22, hardware inventory commands for `safe` tier. The one additive item in this milestone; sequenced last since it's new surface area, not a gap being closed.

## #22 design (settled in this brainstorm)

Candidate commands: `lscpu`, `uname`, `free`, `lsblk`, `df`.

**Split by whether the command takes meaningful user-supplied positional input:**

- `lscpu`, `uname`, `free` take no meaningful path/positional argument, they're flag-only inventory snapshots. Add directly to `safe_rules()` as allows reachable via `run_command`, no dedicated router needed.
- `lsblk`, `df` can take an optional device/path argument (`lsblk /dev/sda`, `df /home`), user-controlled input reaching argv. Add dedicated tool routers (matching the existing `dnf.rs`/`systemctl.rs`/`network.rs` pattern) that inject a `--` separator before any path argument, plus a corresponding `tiers.rs` allow rule.

**Verification requirement, not optional:** before finalising any of these as an unconditional allow, live-verify each command's actual flag surface in a Fedora container. This patch's own history (four rounds on #41's dnf regex, two reopens on #40's systemctl deny) is direct evidence that reasoning about CLI behaviour without checking real output misses real gaps. If a flag turns out genuinely dangerous (writes to disk, or an abuse vector like `free -s` running indefinitely under an attacker-chosen interval), add a scoped deny the same way `top -c` and ping's abuse flags are handled elsewhere in `tiers.rs`.

## Process notes carried into every sub-release's plan

- Each plan's Global Constraints section should restate the project-wide requirement that all four cargo gates (`fmt`, `clippy`, `test`, `build --release`) run clean in a Fedora container, since this crate's privilege-drop code is Linux-only.
- Each plan closes with the same whole-branch final review, fix-wave, scoped-re-review discipline v1.0.1 used, including escalating any fix-loop round 4-5 to a higher-tier reviewing model.
- Each sub-release gets its own CHANGELOG.md entry under a `[1.1]` heading (or its own patch-style heading if Simon wants these released incrementally rather than batched into a single v1.1 tag, not yet decided, raise at the point the first sub-release is ready to ship).
